# HEIC decoder and relocation — W-009 preparation

This isolated C++ experiment decodes real HEIC files through **libheif 1.23.4 + libde265 1.1.1**, using two private shared libraries. Sixteen self-generated fixtures cover all eight EXIF orientation values with opaque and transparent images. A relocated Mac directory passes the same checks with runtime plugin search disabled. This establishes a local candidate path; Windows clean-machine decoding, release authorization and W-031/V-07 remain unverified.

## Pinned dependencies and build

The official release source archives were independently SHA-256 checked against GitHub's published digests. URLs, sizes, hashes, license files and staged library identities are recorded in `docs/windows/evidence/heic-preparation.json`. No upstream source changes, system package installation or binary commits were made.

Download and extract [libde265 1.1.1](https://github.com/strukturag/libde265/releases/tag/v1.1.1) and [libheif 1.23.4](https://github.com/strukturag/libheif/releases/tag/v1.23.4) into an external source directory. Example Mac commands from the repository root, using CMake 3.31.6:

```sh
cmake -S <SOURCES>/libde265-1.1.1 -B <DE265_BUILD> \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=<PREFIX> \
  -DBUILD_SHARED_LIBS=ON -DENABLE_DECODER=OFF -DENABLE_SDL=OFF -DENABLE_SHERLOCK265=OFF
cmake --build <DE265_BUILD> --parallel 6
cmake --install <DE265_BUILD>
cmake -S <SOURCES>/libheif-1.23.4 -B <HEIF_BUILD> \
  -C experiments/windows/heic/codecs.cmake -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_INSTALL_PREFIX=<PREFIX> -DCMAKE_PREFIX_PATH=<PREFIX>
cmake --build <HEIF_BUILD> --parallel 6
cmake --install <HEIF_BUILD>
cmake -S experiments/windows/heic -B <PROBE_BUILD> \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=<PREFIX>
cmake --build <PROBE_BUILD> --parallel 6
```

`codecs.cmake` enables only the built-in libde265 HEVC decoder and disables dynamic plugin loading and all optional external encoders/decoders. Runtime enumeration asserts exactly that decoder and **zero HEVC encoders**. libheif always retains its internal `mask` encoder; the probe checks and reports it instead of claiming no encoders exist. The unused upstream `heifio` build can discover host PNG/TIFF/zlib support, but those libraries do not appear in the staged decoder's actual linkage and its static helper archive is not staged.

The probe has warnings-as-errors enabled. The dependency Debug build emitted four upstream `sprintf` deprecation warnings; no warning suppression or upstream patch was introduced. The final staged binaries dynamically depend only on libheif, libde265 and the Mac C/C++ system runtime.

Windows is an unexecuted build candidate using the same CMake settings under a Visual Studio x64 environment. It will need its actual DLL/CRT dependency inventory and a clean-machine run; the Mac relocation result is not a substitute for that evidence.

## Fixtures and checks

The checked-in corpus is `docs/windows/fixtures/heic`: 16 HEIC files, 16 Mac PNG references, one case table and a checksum manifest for those 33 files. These are original geometric pixels generated by this repository's `generate.swift`; no third-party photo rights are involved. They are 96×64, or 64×96 after orientation, with distinguishable color quadrants and alpha bands. ImageIO performs real HEVC encoding; the reference uses actual ImageIO decode plus CoreImage EXIF orientation and sRGB rendering. These are not historical phone/camera files or lossless source-pixel references.

Regenerate into a new external directory with `swift experiments/windows/heic/generate.swift <NEW_DIRECTORY>`. Encoder bytes can vary with OS/toolchain, so regenerated files must not silently replace the frozen corpus. Current generation used macOS 26.5.1 / Xcode 26.6. No Mac application XCTest was run or claimed for this reference script.

```sh
python3 -m venv <INSPECTION_VENV>
<INSPECTION_VENV>/bin/python -m pip install -r experiments/windows/heic/requirements.txt
LIBHEIF_PLUGIN_PATH=/nonexistent <INSPECTION_VENV>/bin/python \
  experiments/windows/heic/screen.py docs/windows/fixtures/heic \
  <PROBE_BUILD>/heic_probe <NEW_OUTPUT_DIRECTORY>
```

The C++ program reads file bytes into owned storage, retained until the context is released, and selects the libde265 decoder explicitly. It keeps the library's security limits, tightening pixel count to the supplied budget (default 100 MP), and checks the 30,000-pixel side limit before decode. A 256 MiB compressed-file ceiling and one-primary-image rule are experiment constraints, not final product decisions. Strict decoding must produce no warnings. Crop/rotation/mirror handling stays enabled; decoded RGBA8 rows are copied according to the returned stride before library resources are released. Source ICC bytes, when present, are copied separately.

| Check | Final result |
| --- | --- |
| Actual HEVC decode / dimensions / orientation | 16/16 passed, all eight orientation values |
| Alpha and storage | 16/16 exact against Mac reference; straight RGBA8, correct row stride; opaque/alpha metadata matches |
| RGB comparison | Every opaque case has 4,608 differing pixels, every alpha case 2,304; maximum premultiplied channel error 1/255, alpha error 0 |
| Non-ASCII path | A copied rotated/alpha input decodes to identical pixels on Mac |
| Failure paths | Truncated file, PNG masquerading as input, missing file and 100-pixel budget rejected before publishing an output directory |
| Existing output | Refused with original pixels unchanged |
| Corpus integrity | All 33 hashes checked before/after; previous 242 fixed files unchanged |
| ASan/UBSan | Probe **and both dependencies** rebuilt with instrumentation; complete harness passed; system libraries uninstrumented, leak detection disabled |
| Relocated Release / sanitizer | All 50 raw/PNG artifacts byte-identical, including 17 raw decodes, 32 result/difference PNGs and the contact sheet |

No RGB tolerance is accepted. The color-quadrant diagnostic sheet shows correct rotation/mirroring/transparent bands and uniform one-unit color differences. It does not prove photographic detail, general color conversion or visual acceptance.

These generated files report zero raw ICC bytes. Therefore the ICC-copy branch and non-sRGB ICC conversion are **not tested**. HDR, 10/12-bit, NCLX variants, EXIF-only orientation without container transforms, DPI, auxiliary depth/gain maps, multiple primary images, real tiled camera images, large files, fuzz/security coverage and cancellation remain open for W-031/V-07. The default libheif output color handling was retained; it is not a chosen HDR policy.

## Local relocation and distribution candidate

The observed external stage contains `heic_probe` (62,720 bytes), `libheif.1.dylib` (1,910,216 bytes), `libde265.0.dylib` (463,600 bytes), and both upstream COPYING files. On this Mac the executable's prefix RPATH was replaced with `@loader_path`, its local ad-hoc signature refreshed, and the directory moved to `/tmp/compositor-heic-relocated`. Example reproduction:

```sh
mkdir -p <STAGE>/Licenses
cp <PROBE_BUILD>/heic_probe <STAGE>/
cp -L <PREFIX>/lib/libheif.1.dylib <STAGE>/
cp -L <PREFIX>/lib/libde265.0.dylib <STAGE>/
cp <SOURCES>/libheif-1.23.4/COPYING <STAGE>/Licenses/libheif-COPYING
cp <SOURCES>/libde265-1.1.1/COPYING <STAGE>/Licenses/libde265-COPYING
install_name_tool -rpath <PREFIX>/lib @loader_path <STAGE>/heic_probe
codesign --force --sign - <STAGE>/heic_probe
mv <STAGE> <RELOCATED_STAGE>
DYLD_PRINT_LIBRARIES=1 LIBHEIF_PLUGIN_PATH=/nonexistent \
  <RELOCATED_STAGE>/heic_probe docs/windows/fixtures/heic/orientation-6-alpha.heic <NEW_OUTPUT>
```

The loader trace confirms both decoder libraries come from the relocated directory, with no Homebrew/prefix path. The full 16-case harness also passes there. This is a local development stage, not a shipped installer or release signature. On the 64×96 alpha specimen, one standalone Release process recorded 0.458833 ms read/decode/copy, 0.06 s wall and 3,424,256 bytes maximum RSS. This tiny sample excludes Python/reference generation and cannot establish Windows memory, large-image performance or long-run behavior.

Both libraries' source headers use LGPL-3.0-or-later; their [libheif COPYING](https://github.com/strukturag/libheif/blob/v1.23.4/COPYING) and [libde265 COPYING](https://github.com/strukturag/libde265/blob/v1.1.1/COPYING) include the license texts. A candidate distribution would retain replaceable shared libraries, notices and exact corresponding source/build instructions. Final package obligations, codec patent/distribution questions and D-07 approval are still unresolved. Dynamic linking and successful decoding alone do not establish release clearance.

Evidence: `docs/windows/evidence/heic-{macos,preparation}.json`, `heic-contact-sheet.png`. Release output is `/tmp/compositor-heic-run-02`; sanitizer is `/tmp/compositor-heic-run-sanitized`. Their logs use the same path plus `.log`. The native resource log is `/tmp/compositor-heic-metrics-resources.log`. W-009, W-031, M1 and release gates remain unpassed; no remote CI or Windows execution occurred.
