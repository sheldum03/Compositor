# S05 R7：减少测试报告的分配（2026-09-23）

实际 `SaveLong` 调用测量确认：完整报告先序列化为 UTF-16 字符串，再写 UTF-8 文件，在九轮中额外产生约 1 GiB 分配。R7 直接用 `JsonSerializer.Serialize(Stream, ...)` 写文件，保留报告字段、缩进、100 次检查点、工作负载和 GC 策略。没有修改笔刷算法或 S02 标准。

## 测量与回归

Mac arm64、.NET 10.0.12，同一九轮 `--s05-soak-check`；在同步写出前后用 `GC.GetAllocatedBytesForCurrentThread()` 测量，输出 `[DEBUG-s05-report]`，日志输出本身在计量区间外。两次均正常退出，900 次编辑/撤销/重做、18,900 个回调与独立复核通过。

| 测量 | 原写法 | 流式写出 |
| --- | ---: | ---: |
| 写出次数 | 100 | 100 |
| 写出累计分配 | 1,061,944,608 B | 17,444,128 B |
| 累计文件输出 | 505,273,793 B | 504,161,997 B |
| 写出累计耗时（单次观测） | 1124.46 ms | 915.63 ms |
| 最终诊断 GC 前的总分配估计增量 | 5,520,310,000 B | 4,515,365,768 B |

写出分配下降 98.36%。排除最后两次（在资源采样之后）的写出后，其余分配估计分别约 4,497,947,776 B 与 4,498,288,816 B，支持这次下降主要来自报告写出。两次的动态计时与资源数字不同，故整个文件长度略有差异；这不是逐字节比较的方法。耗时没有做重复统计，不作笔刷速度提升结论。

回归断言针对实际调用日志，要求 100 次写出且累计分配小于累计文件字节数：基线失败（比值 2.102），修改后通过（0.0346）。这是消除完整字符串分配的诊断断言，不是新造的 S05 内存验收标准。原始日志、临时插桩源码和断言脚本一起保存在本地证据包，插桩不进入交付 DLL。

另在原三轮工作负载的实际调用点，对同一个报告对象执行新旧两种写出，34 次 UTF-8 字节比较全部相同。此验证单独运行，避免双重写出污染性能对比。移除插桩后再次运行原三轮测试，退出 0、独立复核通过。全部 48 张 4000×4000 final/reopened 图像解码后的 RGBA 与 Windows R6 相同，共同 SHA-256：`a8a62c6c48e71e2ce419ee56802d7160c0beaeded89c386d903ac60deba58a8e`。

Windows x64 发布成功；24 项锁定依赖定义、版本和 contentHash 未改变。使用独立临时 RID 锁文件，仓库锁文件未改。交付源码已移除所有诊断日志。[量化结果](r7-allocation-comparison.json)。

## 限制与实机复核

这只确认了测试工具的额外分配，未证明 Windows 专用内存会相应下降，也没有证明其他约 4.5 GB 分配不再需要优化。下一步在 Windows 同机运行原 R6 的九轮加 60 秒空闲流程，校验完整结果后比较资源趋势。资源验收、M1 选型与完整 Windows 1.0 仍未完成。

.NET 10 的反射序列化流式分支会分段写出并清空缓冲区，见 [运行时实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Text.Json/src/System/Text/Json/Serialization/Metadata/JsonTypeInfoOfT.WriteHelpers.cs)；本次结论仍以实际调用测量为准。
