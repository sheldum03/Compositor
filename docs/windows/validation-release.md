## 2. 工程与图像样本

M0 先使 Mac 测试 target 可编译并跑相关回归，再固化参考结果；现有版本 1–7 测试使用空文档，不能替代真实功能/资源样本。M0 新建样本清单，每条记录 ID、来源/使用权、基线提交、生成步骤、manifest 版本、预期元数据、像素 hash 或参考图及容差类别。先用程序生成几何/透明度/噪声图，避免引入来源不明素材；AI 另用有使用权的图片集。

建议样本组：

- F01：v1 基础图像/尺寸/分辨率；F02：v2 组；F03：v3 混合透明度；F04：v4 栅格蒙版。
- F05：v5 剪贴链；F06：v6 组蒙版；F07：v7 调整层；F08：v8 文本。
- F09：当前版本的 maskPlacement/maskLinked、形状、空图层、复杂层级和多种混合叠加。
- F10：缺文件、坏 PNG、重复 ID、循环组/蒙版链、路径逃逸、超限尺寸、非有限值、未来版本。
- F11：中文/英文/Emoji/组合字符、固定框、多行、左右中对齐、字号/行距/字距及 72/300 DPI。
- F12：同字体、缺失字体、同名不同字体、损坏/空字体、TTC 多 face、导入后重启。

旧版本样本必须来自可验证的旧版编码或严格按该版本 schema 生成；不能仅修改 v8 的版本数字。至少保留一套“Mac 保存 → Windows 修改/保存 → Mac 重开”的完整文件与结果；反向也要验证。

文本旧缓存和新布局结果分别验收：未编辑打开应使用保存像素；明确编辑后的跨平台字形不要求 bit-exact，但内容、样式、命中与预览/导出必须一致。

## 3. 正确性判定

| 对象 | 比较方式 | 通过标准 |
| --- | --- | --- |
| manifest 语义 | 解码后的规范化字段比较，不比较 JSON 文本排序 | 所有已定义字段和值保留；默认值和明确允许的版本升级单列 |
| 未修改资产 | 解码像素、尺寸、灰度/alpha 比较 | 保持像素意义；重新编码压缩字节可以不同 |
| 固定整数像素算法 | 同输入/seed 的原始输出比较 | 无差异；若算法原本含浮点或平台舍入，先归类再设阈值，不擅自放宽 |
| 重采样、模糊、浮点合成 | 最大/平均误差、超阈值像素比例、差分热图与人工边缘检查 | M0/M1 为各操作确定容差并提交记录；不得统一用一个 SSIM 分数放行 |
| 同一 Windows 后端的预览/导出 | 排除缩放采样差异后比较同区域 | 图层/蒙版/调整规则一致，无漏层、错色或错误裁切 |
| GPU 与 CPU | 相同输入和数值约定的对照 | 采用对应算法容差，不允许通过改变实际工具语义消除差异 |

参考基线存在缺陷时，先登记“基线偏差”和期望结果；修复后的 Windows 行为不能伪装成逐像素兼容。必要的 Mac 修复另立任务。

## 4. 笔刷、历史与异步的必测序列

软硬笔刷分别测试 12/40/520/800 px、低/满不透明度、稀疏/密集采样、交叉和锐角。覆盖空图层、已有图层、缩放旋转图层、选区、栅格/组蒙版。抬笔后立即下一笔、撤销、重做、导出、保存重开均应正确。

M1 即运行最小完整笔划循环，而非只调用 C 像素函数。分别记录 Mac CPU dabs 与 Metal 连续密度参考；确定 Windows 算法/容差，不能假定两者逐像素一致。

特别检查：临时笔尾替换无旧残影；瓦片边界无缝；已保存历史不被后续写入修改；提交不强制物化整幅连续大图；一次笔划只产生一个历史项。

后台序列包括：开始滤镜→取消、开始推理→尝试切换项目、保存中尝试画笔、关闭项目→后台任务返回。对当前阻止重叠操作的策略，验证请求被阻止且结束后正常恢复；若某功能允许切换/继续编辑，再验证过期任务与保存快照 revision。过期结果不能写回新文档，取消不产生新的脏状态。

## 5. 文本与输入法必测序列

选择微软拼音及至少一种目标用户常用中文输入法；记录版本。验证候选选词、组合态 Esc/Enter、粘贴、撤销、换工具/切标签/保存时的处理，不只测试最终提交的中文字符串。

输入光标、选择高亮和点击命中在缩放、旋转、水平/垂直翻转、非等比缩放后与文字一致。空文本取消不产生图层/历史；字号越限时保留可编辑草稿；重新编辑既有层不改 ID/父组/效果。

缺失字体工程打开保持原 PNG；仅移动/旋转不替换字体；显式替换可撤销。损坏字体不写入用户字体库，同名不同内容的字体冲突可见，TTC 枚举每个 face，重启后字体仍可用。

补充 D-11 样本：有字体/缺字体时缩放文字层；移动/旋转/镜像且栅格尺寸不变；像素操作与 Image Size 后 text 元数据、undo/redo 和重开。当前 Mac 缩放会重绘，Image Size 会清除 text，先记录决定后的预期，不把它们与未编辑往返使用同一标准。

复用测试意图来源：`TextToolTests.swift`、`TextLayoutTests.swift`、`FontLibraryTests.swift`。现有源码/格式文档对文本编辑预览若有描述差异，在 M0 实际复现并决定，不直接复制过时文字。

## 6. 性能场景与拟定门槛

参考机建议至少 16 GiB RAM、SSD、Windows 11 x64，并提供一台常见集成显卡设备；具体 CPU/GPU/驱动与系统版本在 M0 实录。门槛只对冻结的参考机适用，不对所有 Windows 电脑做承诺。

| 场景 | 固定工作负载 | 拟定门槛/用途 |
| --- | --- | --- |
| S01 | 4000×4000 文档、单张不透明图，1000×1000 逻辑像素视口；平移/缩放 | 更新事件处理至提交显示工作 P95 ≤16.7 ms |
| S02 | 同尺寸；800 px、0% 硬度、100% 不透明度；每笔 120 次固定路径更新；空层/已有层各测 | 更新 P95 ≤16.7 ms；mouse-up 至历史提交 P95 ≤100 ms；无 AI 时进程峰值专用内存目标 ≤2 GiB |
| S03 | 4K 文档、一张 4K 底图与 19 张 512×512 图层，含组/蒙版/混合；总源像素不超过格式限额 | 正确性必过；M1 记录基础值，M3 冻结多层性能预算，作为后续回归场景 |
| S04 | 8192×8192 单图层及局部蒙版，局部画笔/导出/撤销 | 压力场景：不崩溃、不破坏工程；单独测 RAM/VRAM，不承诺与 S02 同耗时 |
| S05 | 连续 100 次局部编辑→撤销/重做→关闭工程，重复 3 轮 | 无单调累积的非预期占用；区分缓存上限与泄漏，M1 定稳定后可接受波动 |

所有尺寸和图层组合保持在当前格式的源像素/蒙版预算内。8K 单幅 RGBA8 原始平面为 256 MiB，仅是宽×高×4，不含快照、蒙版和 GPU 副本。

测试统一 Release、同一设备、输入路径/seed/视口/缩放和电源状态；冷启动与预热分开。每组至少 30 笔，报告每次 pointer update 与每次 mouse-up 的分布；同时保存原始样本，不只报一个均值。

采集 CPU 时间、GPU 时间、等待时间、上传/回读量、进程专用内存和显存。软件事件耗时不能冒充输入到屏幕的延迟；如需后者另用可验证的显示测量方法。普通无 GPU 的 CI runner 只验证功能，不用于最终性能判定。

M1 对代表笔划测量并判断技术路线可行性，M5 对完整工具组合优化。超过预算先查分配/整图复制/缓存失效/同步等待，再考虑 GPU；若 CPU 底座不满足冻结门槛，不能直到 M5 才首次验证 GPU 备选。如确需改变门槛，记录原因与范围影响，不在失败后悄悄改硬件或场景。

## 7. AI 与颜色验收

AI 样本建议至少 30 张，覆盖人像发丝、毛发、商品、透明/半透明边缘、低对比、多主体和无明显主体。M1 先验证一条真实候选模型的输入/输出与部署可行性，M6 再做完整效果验收。模型效果相对 Mac Vision 做可见差异记录，但不以“看起来先进”替代用户可接受性判断。

逐模型记录权重来源/hash/许可、输入规格、CPU 与可选 GPU 的首推/热推耗时、内存/显存、包体增量、算子兼容与错误路径。M6 根据实际样本决定质量与时间门槛；未决定前不得宣传模型已达到产品效果。

没有模型、下载中断、校验失败、推理取消、CPU fallback 和离线重启都要测。模型装好后的编辑不能依赖远程服务，图片不得作为模型下载或更新请求的附带内容。

图像 IO 用 RGB/sRGB、嵌入非 sRGB profile、EXIF 旋转、灰度、透明边缘、不同 DPI 与损坏文件验证。TIFF/HEIC 必须在干净系统使用实际发行包打开，不以开发机安装的额外插件作为证明。JPEG 有损比较与 PNG 无损比较采用不同标准。

## 9. 安装、更新与数据恢复

候选包包括运行所需 DLL/运行库、必要字体、许可证和版本信息。AI 权重是否随包或首次下载由 D-08/D-09 决定；不附带模型时，核心编辑仍应正常启动和使用。

基础安装/卸载在普通用户权限下验证；更新需验证旧版本到新版本、正在编辑时延后重启、下载失败、坏签名/校验失败、文件被占用和重启后的可用性。安装器与自动更新不能删除用户工程、导入字体和非自有目录。

目录工程保存的故障注入点：写 manifest 前/后、写资产中、临时包校验后、旧目录备份后、新目录切换前/后。每一点都验证重启后能找回完整旧版或完整新版，不出现“保存成功但工程残缺”。恢复策略不可仅靠测试脚本代替应用行为。

发布包代码签名、更新元数据/包真实性校验分开验证。先在测试渠道用候选版本走通，再开放正式更新源。密钥、证书和访问令牌不入仓库；缺签名资源时只能交付明确标记的内部测试包。

## 10. 1.0 发布门槛

- P-01 至 P-19 范围内需求全部有通过记录；Beta 后未解决的缺项不能以“已知问题”绕过核心范围。
- 数据损坏、丢层/丢文本、保存失败误报成功、普通路径崩溃、更新后无法启动等发布阻断问题为零。
- 所有基线工程版本通过读写验证，完整跨平台往返经过 Mac 和 Windows 双端确认。
- S01/S02 满足冻结门槛，S03–S05 符合各自预算/稳定性标准；偏差须显式决定，不伪装成通过。
- 干净机安装/启动/解码/导出/卸载/更新通过；实际包与测试包一致。
- 依赖、字体与模型权重的版本/许可清单完整，用户说明、限制和版本记录齐全。
- 发布记录包含源码提交、构建配置、依赖清单、包 hash、签名验证结果、设备与 V 编号测试结果。

发布是后续执行任务，本轮文档不意味着已经授权向任何网站或更新渠道上传二进制。
