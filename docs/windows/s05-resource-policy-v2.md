# S05 资源规则提案 v2（2026-09-24）

状态：**两个独立 Windows 进程的前瞻复核已通过；仅接受固定原型路径的资源检查，不是完整产品验收**。规则正文与判定器保持运行前提交 `8a4d1d8` 的内容。v1 规则、判定器和首轮失败保留；不更改应用、GC 配置、S02 门槛或原始数据。结果见 [限定范围评审](evidence/lifecycle-s05/resource-policy-v2/prospective-review.json)。

## 改动及原因

v1 将第 10–18 轮的关闭后上限作为第 19–27 轮的唯一参照。首轮实机失败的后段上限仍低于第 1–9 轮已经出现的上限。为检验规则本身，构造固定 18 轮周期：最低占用恒为 350 MiB，第 2 点为 512 MiB，第 11 点为 448 MiB，其余为最低值。重复该周期，没有任何累积项。

同一周期取 18 个不同起点，v1 的上限检查出现九次失败、九次通过。这证明该检查对这类有界波动的分段位置敏感；不证明 Windows 应用没有泄漏，也不代表真实 GC 必然按该周期工作。

v2 **只改变上限参照**：后九轮的最高值与前 18 轮已出现的最高值比较，允许增长仍为 32 MiB。关闭后最低值仍比较第 10–18 与 19–27 轮，增长限制仍为 32 MiB，避免早期峰值掩盖不断上升的底部。

| 检查 | v2 规则 |
| --- | --- |
| 自然采样专用内存 | 所有样本 ≤ 1 GiB，包括启动/预热与每次更新记录 |
| 关闭后最低值 | 第 19–27 轮最低值 ≤ 第 10–18 轮最低值 + 32 MiB |
| 关闭后新高水位 | 第 19–27 轮最高值 ≤ 第 1–18 轮最高值 + 32 MiB |
| 关闭后句柄 | 第 19–27 轮最低/最高值分别 ≤ 第 10–18 轮对应值 + 8 |
| 自然空闲 | 每个空闲样本 ≤ 最后关闭样本 + 32 MiB |
| 最终诊断 GC | 旧文档弱引用为零，托管存活量 ≤ 64 MiB；不能在自然样本之前执行 |

其他范围、数值依据及限制沿用 [v1](s05-resource-policy.md)。v2 不保证所有周期/相位不被拒绝，不排除小于检测灵敏度的泄漏，也不将进程专用内存减去 GC committed 当作原生泄漏估算。

## 判定器与验证顺序

1. 固定本规则、[v2 判定器](../../experiments/windows/avalonia/review-s05-resources-v2.py)及其依赖的原 v1 判定器 → 提交后才开始新 Windows 运行。
2. 执行[控制样本](../../experiments/windows/avalonia/check-s05-resource-v2-controls.py) → 所有周期起点通过；持续增长、早期高峰后的底部增长、残留一幅 4K RGBA 图像、新高峰、句柄/空闲增长、旧文档残留和超预算必须拒绝；完整性错误仍由实际 CLI 拒绝。
3. 旧两轮实机报告仅作校准 → v1 原失败不改，v2 对旧数据的结果不构成前瞻验收。
4. 用相同诊断 DLL、样本及运行库，运行两个新的独立 Windows 进程 → 每轮均保留退出码、环境、原报告、归档及 54 张图片独立复核。
5. 两轮全部通过才评审冻结这条固定原型路径的资源判断 → 判定器始终输出 `resourceAccepted=false`，需要结合完整证据评审；不能作为完整产品、设备矩阵或发布验收。

运行：`python experiments/windows/avalonia/review-s05-resources-v2.py <run/report.json>`。它先执行既有 27 轮完整性检查，复用 v1 的资源字段验证和未改变的检查，并保留原 v1 上限检查结果供审计。

控制与校准记录见 [证据目录](evidence/lifecycle-s05/resource-policy-v2/README.md)。
